# 04 · Content format and rendering

Goal: every equation, code listing, table, diagram and flow is stored as **structured data**, validated by scripts, and rendered by one renderer that we control. No raw HTML, no pasted images of equations, no hand-placed pixels.

## 1. Authoring format

A chapter is one JSON document (authored through a small Markdown-like front end that compiles to it; see §6). It is a tree of **blocks**. Order and required blocks are enforced by schema.

```json
{
  "id": "cs.os.deadlock",
  "title": "Deadlocks",
  "syllabus_refs": ["CS 5: Operating System / Deadlock"],
  "prereqs": ["cs.os.process-synchronisation.semaphores"],
  "topics": [
    { "id": "cs.os.deadlock.coffman", "title": "The four conditions",
      "blocks": [ { "type": "hook", "...": "..." }, { "type": "intuition", "...": "..." } ] }
  ]
}
```

### Required order inside every topic (schema-enforced)

1. `hook`: one or two sentences: why this topic exists, a real situation.
2. `intuition`: the idea in plain words with the first picture (diagram/analogy).
3. `definition` / `theorem` / `formula`: the exact statement (typeset).
4. `derivation` or `walkthrough`: how we get there, step by step (where the topic has one).
5. `example` (one or more): fully worked, numbers verified by script. At least one is marked `pyq` when a real GATE question fits.
6. `trap`: the common mistake and why it is wrong.
7. `shortcut` (optional): when a faster method exists, with the condition under which it is valid.
8. `gate-note`: how GATE asks it (question types, typical numbers, frequency from the bank).
9. `recall`: the one-screen recall card (see `06`).
10. `check`: 3 to 5 questions (MCQ/MSQ/NAT) with worked solutions.
11. `pyq-links`: generated from the bank by tag (not hand-written).
12. `references`: sources learnt from (see `03`).

## 2. Block catalogue (every block type and its exactness rule)

| Block | Content | Exactness rule |
|---|---|---|
| `text` | Paragraphs with inline emphasis, inline TeX `\( \)`, inline code, term-links | Terms in the glossary are auto-linked; no free HTML |
| `equation` | Display TeX, optional number and name | Must compile; numbered equations are referenced by ID, never by "above" |
| `derivation` | Aligned multi-line TeX with a justification per line | Each step's justification is a required field; a checker verifies symbolic equivalence where possible (SymPy) |
| `formula` | A formula card: symbol table (symbol, meaning, unit, range) plus conditions of validity | Units and symbols table required; symbols used in the formula must all appear in the table |
| `definition` / `theorem` / `lemma` | Named, with `statement`, optional `proof` | A theorem without a proof sketch or a citation fails |
| `example` | `given`, `find`, `steps[]`, `answer`, `verify` (script ref) | `verify` script must reproduce `answer` and every numeric step |
| `code` | `language`, source, optional `output`, `highlight` lines, `annotations` by line, `runnable` flag | Executed in the sandbox; stated output must match; line annotations must point to real lines |
| `pseudocode` | Our fixed pseudo-code dialect (indentation-based, keywords typeset) | Parsed by our small checker; invalid pseudo-code fails |
| `trace` | An algorithm trace table: variables per step | Generated by running the algorithm in the verify script, never typed by hand |
| `table` | Data-driven table (columns with types: text, number, unit, TeX), caption, source | Rectangular; totals recomputed; units consistent |
| `diagram` | Typed diagram data (see `05`): graph, tree, automaton, state machine, block diagram, timing, memory/stack layout, circuit, free-body, geometry, plot | Validated structure + alt text; rendered to SVG |
| `flow` | Flowchart / algorithm flow / decision tree as nodes and edges | Single entry, all paths end, no dangling edge (validated) |
| `plot` | A function or dataset plot from the data itself (not a screenshot) | Axes labelled with units; computed from the same formula the text states |
| `trap` / `shortcut` / `gate-note` / `remember` | Callout boxes with a fixed colour and icon | One idea per callout; `shortcut` must state its validity condition |
| `compare` | Side-by-side comparison table of two or three concepts | Same attributes for every column |
| `recall` | The recall card: cue → answer pairs, mnemonic, one-line summary, "if you forget everything, remember this" | ≤ 60 words of recall text on the card |
| `check` | Question with options/answer/solution and the topic tag | Same schema as bank questions, so the existing practice engine can run them |
| `callout-warning` | "Out of syllabus", "advanced optional", "changed in 2027" | Required wherever applicable |

## 3. The renderer

- **One renderer**, a React component set (`components/study/*`) that maps block types to components. Unknown block types fail the build; there is no HTML pass-through, so a content error can never become a markup injection.
- **Equations:** TeX → **SVG paths** with MathJax SVG output (already in the app through `better-react-mathjax`). Choosing SVG path output means the equation is not selectable text in the DOM (which also helps protection) and renders identically on every device. Long equations scroll horizontally inside their own box on narrow screens and never overflow the page; display equations can switch to a stacked layout via `\\` at a configured width.
- **Code:** a custom tokenizer-based highlighter (no heavy library), monospace, line numbers, highlighted lines, annotation chips, light and dark themes. Copy is disabled in protected mode (see `07`); a "copy" affordance is offered only for short snippets the author marks `copyable` (so students can paste a template into the practice editor).
- **Tables:** real semantic `<table>` for accessibility, but with the text drawn through the protected text layer (see `07`). Wide tables get a sticky first column and horizontal scroll; very wide tables get a "rotate" or "card" layout on phones, chosen per table by the author.
- **Diagrams and flows:** rendered from data to inline SVG at runtime by our diagram engine (see `05`). Theme-aware (light/dark), scalable, with text as real SVG text only when protection allows, else as paths.
- **Layout:** one reading column (max ~72 characters), generous spacing, sticky outline, progress bar, estimated time, keyboard navigation, reduced-motion respected.
- **Print:** disabled for protected content (see `07`); there is a separate, deliberately minimal "recall sheet" view per chapter for on-screen revision.
- **Performance:** the chapter is fetched as one compressed, encrypted bundle (typically 20 to 80 KB per chapter), decrypted in memory, and rendered incrementally; images do not exist (everything is vector), so there is no image weight. Lazy-load diagrams below the fold.

## 4. Exactness rules that apply everywhere

1. **Numbers in text come from scripts.** Any numeric value in an example must exist in the example's `verify` output; a lint rule rejects a number that is not in the verify output or defined as a constant.
2. **Units always.** Physical quantities carry units; a unit-aware checker (dimensional analysis on the TeX where feasible, and a required `unit` field in the symbol table) flags mismatches.
3. **One symbol, one meaning per chapter.** The symbol table of each formula card is the contract; reuse of a symbol with a different meaning fails lint.
4. **Code is real.** Every code block runs; the output shown is the real output; platform dependencies (for example `sizeof(int)`) are stated.
5. **Standards-based facts are cited** (protocol constants, IS-code clauses, instruction latencies) with the clause or RFC number.
6. **Rounding** follows GATE's rule: say how many decimals and whether the answer is a range.
7. **No ambiguous notation.** `log` always has an explicit base unless it genuinely does not matter, and then we say so.

## 5. Data model (storage and API, outline)

- **Private source:** the JSON files above in git (private repository; verify the repo is private before the first real chapter is committed).
- **Published form:** one encrypted bundle per chapter (AES-GCM, key per chapter, key wrapped per user/session; see `07`). Bundles are served from the Worker or Supabase Storage as opaque bytes; they contain no readable text.
- **Tables (Supabase):** `study_chapters` (id, branch, version, hash, status, price tier), `study_access` (user_id, branch, source, valid_until), `study_progress` (user_id, topic_id, state, last_read_at, time_spent), `study_reports` (issues), `study_notes` (per-user notes). All with RLS, same pattern as `entitlements`.
- **API:** `/api/study/tree` (public skeleton: titles and structure only, for SEO and the free preview), `/api/study/chapter/<id>` (requires access; returns the wrapped key and bundle URL), `/api/study/progress`.
- **Free preview:** the first topic of the first chapter of each subject is free and **visible to search engines as normal HTML** (this is deliberate marketing). Everything else is protected.

## 6. Authoring ergonomics (so the volume is feasible)

- Authors (Claude) write chapters in a compact Markdown dialect with block fences (`:::example`, `:::trap`, `:::diagram graph`…). A compiler turns it into the JSON schema and reports precise errors with line numbers.
- **Snippet library:** reusable, verified blocks (for example the standard "binary search trace", the "page-table address translation" diagram) referenced by ID, so we do not redraw or retype.
- **Live preview** (`npm run study:preview <chapter>`) renders the chapter exactly as students see it, with the validators' results beside it.
- **Golden tests:** each block type has a golden rendering test (screenshot diff in the full test matrix: desktop and mobile, light and dark) so renderer changes cannot silently break old chapters.
